# 01 · 项目总览：它是怎么跑起来的

> 这一章不写代码，只讲清楚"这个项目到底在干什么"。读完你就能跟别人解释这个项目了。

## 一句话概括

**把一条 B 站视频链接，变成一份可以复习的 Markdown 笔记 + 一张可以导出 XMind 的思维导图。**

它做的事情，本质上是三件：

```
① 把"声音/字幕"变成"文字"        （信息获取）
② 把"一大堆文字"变成"结构化知识"   （信息压缩，靠大模型）
③ 把"结构化知识"变成"给人看的东西" （Markdown 文件 + 脑图）
```

## 为什么需要它

假设你看了一个 1 小时的 B 站技术视频：

- **直接看**：60 分钟，看完就忘，想复习得重新拖进度条。
- **自己记笔记**：边看边记，效率很低，而且容易漏。
- **用这个工具**：粘贴链接 → 等 1-3 分钟 → 得到一份带时间戳的笔记。

笔记长这样（真实产物见 [`docs/sample/sample.md`](sample/sample.md)）：

```markdown
# 从零实现 RAG 系统：架构、向量库与召回重排

> **一句话总结**：作者用 3 小时从零搭了一套可用的 RAG 系统……

## 🧭 目录
1. [为什么朴素 RAG 不好用](#...) · [2:05](https://www.bilibili.com/video/BVxxx?t=125)
2. [数据准备与分块策略](#...) · [15:00](...)

## 📖 详细笔记
### 1. 为什么朴素 RAG 不好用
⏱ [2:05 - 15:00](https://www.bilibili.com/video/BVxxx?t=125)
- 朴素 RAG 的三个失效场景：多跳问题、术语指代、需要跨文档汇总
- 把 embedding 当成理解是最大的误解……
```

注意那个 `t=125` —— 点一下就能跳回视频的 2 分 05 秒。这是这个工具最实用的地方。

## 完整流程图

从你在网页上粘贴链接，到拿到笔记，一共经过 **11 个步骤**：

```
[你] 粘贴链接，点「生成笔记」
  │
  ▼
[前端 web/js/app.js]  POST /api/tasks  ──────────────┐
  │                                                  │
  ▼                                                  │
[路由 src/webapi/routes_tasks.py]                     │
  │  ① 校验链接，写一条任务记录到 SQLite              │
  │  ② 丢到后台异步执行（不等它跑完就返回）           │
  ▼                                                  │
[流水线 src/pipeline.py :: run_pipeline]              │
  │                                                  │
  ├─ ③ 解析链接：是不是 B 站？第几个分P？            │
  │     → src/platforms/registry.py 挑平台           │
  │                                                  │
  ├─ ④ 拿视频信息：标题、UP主、分P列表                │
  │     → src/platforms/bilibili.py                  │
  │                                                  │
  ├─ ⑤ 查转写缓存：这个视频以前处理过吗？            │
  │     → src/core/cache.py                          │
  │     命中 → 直接用，跳到第 ⑦ 步                   │
  │                                                  │
  ├─ ⑥ 抓字幕（没有就下载音频转写）                  │
  │     → 字幕：bilibili.py 的 list_subtitles()      │
  │     → 转写：src/asr.py                           │
  │                                                  │
  ├─ ⑦ 调大模型，把字幕变成结构化 JSON               │
  │     → src/llm/notes.py :: generate_note()        │
  │       其中：长字幕会分块 map-reduce               │
  │                                                  │
  ├─ ⑧ 用 Python 模板把 JSON 渲染成 Markdown         │
  │     → 同一个文件的 render_markdown()             │
  │     （注意：Markdown 不是模型写的，是代码拼的）   │
  │                                                  │
  ├─ ⑨ 生成思维导图树（模型重排层级，失败有兜底）    │
  │     → generate_mindmap()                         │
  │                                                  │
  └─ ⑩ 落盘：.md / .mindmap.json / .xmind / .opml    │
        → src/pipeline.py :: save_artifacts()        │
        → 同时在 SQLite 里登记这条笔记               │
  │                                                  │
  ▼                                                  │
[前端] 通过 SSE 实时收到进度 ←────────────────────────┘
  │      （每个步骤都会推一条消息给浏览器）
  ▼
[你] 看到笔记 + 思维导图，点下载
```

**加粗的关键点**：第 ② 步"丢到后台"非常重要。如果不用后台任务，
生成一篇笔记要等 2 分钟，浏览器就会一直转圈直到超时。
这个项目用的是 `asyncio.create_task()`（见 `src/pipeline.py` 的 `spawn_task()`）。

## 五个核心设计决策（面试也能讲）

### 1. 为什么用"后台任务 + SSE"而不是"请求等结果"

同步等待的问题：HTTP 请求会超时、页面卡死、用户不知道进度。
这个项目的做法是：

1. `POST /api/tasks` 立刻返回一个 `task_id`（几十毫秒）
2. 任务在后台 `asyncio` 任务里跑
3. 每完成一个阶段，就往"事件总线"里发一条消息
4. 前端用 **SSE**（Server-Sent Events，服务器单向推流）订阅 `/api/tasks/{id}/events`
5. 页面上的进度条实时更新

代码位置：进度推送看 `src/core/db.py` 的 `EventBus` 和 `emit()`；
订阅接口看 `src/webapi/routes_tasks.py` 的 `events()`。

### 2. 为什么 Markdown 由代码生成，而不是让大模型直接写

❌ 错误做法：`请把字幕总结成 Markdown 笔记` → 模型输出格式每次都不一样，
有时忘了写标题，有时列表缩进错乱，有时夹一句"好的，以下是您的笔记"。

✅ 这个项目的做法（**两阶段**）：

- **阶段 A**：让模型只输出 **JSON**，字段固定：`title` / `summary` / `outline` / `highlights` …
- **阶段 B**：Python 代码按模板把 JSON 拼成 Markdown（`render_markdown()`）

好处：格式永远正确；想改排版只改代码，不用改 Prompt；模型换一个也不影响格式。

### 3. 为什么按"平台"抽象出一层

`BasePlatform` 定义了 4 个方法，任何平台只要实现它们就能接入：

```python
match(url)             # 这个链接归你管吗？
normalize(url)         # 把链接拆成 video_id / page
fetch_info(parsed)     # 拿标题、UP主、分P列表
fetch_transcript(...)  # 拿字幕文本
```

B 站实现了一份（`bilibili.py`，584 行，最复杂），本地文件实现了一份
（`local_file.py`，只有 159 行）。**加 YouTube 只需要再写一份，流水线一行都不用改。**

### 4. 为什么要做转写缓存

一次完整流程里最慢的是"下载音频 + 语音转写"（1 小时视频可能要几分钟）。
同一个视频第二次生成笔记时，如果还要重新转写就太浪费了。

`src/core/cache.py` 用这个规则做缓存 key：

```
平台 + 视频ID + 第几个分P + ASR配置指纹(+ 本地文件的修改时间)
```

换成 `tiny` 模型或换视频文件后，指纹变了 → 自动重新转写。这个设计叫 **缓存失效策略**，
是工程里很常见也很重要的东西。

### 5. 为什么要限制并发

批量提交 20 条链接时，如果同时发 20 个请求，B 站会认为你在爬站 → 返回 412 风控。
所以用 `asyncio.Semaphore` 做闸门（`src/pipeline.py :: configure_concurrency()`），
默认同时只跑 2 个，其余的排队。

## 技术栈一览（以及为什么选它）

| 层面 | 选型 | 为什么 |
| --- | --- | --- |
| 后端语言 | Python 3.10+ | 大模型/语音转写生态最好；`asyncio` 适合这种"等 IO"的任务 |
| Web 框架 | FastAPI | 自带接口文档（`/docs`）、原生异步、类型校验（Pydantic） |
| 数据存储 | SQLite + 本地文件 | 单人自用，零部署成本；笔记是纯文件，方便直接翻看/git 管理 |
| 大模型 | OpenAI 兼容接口 | 一套代码通吃 DeepSeek / 通义 / Kimi / 本地 Ollama |
| 前端 | 原生 JS（无框架、无构建） | 页面不复杂，省掉 Node 构建链；改了刷新即生效 |
| 思维导图 | markmap | 能把 Markdown 直接渲染成脑图，也能导出 SVG/PNG |
| 语音转写 | faster-whisper / OpenAI | 前者本地离线免费，后者开箱即用 |

## 项目规模

```
src/      约 3800 行 Python   ← 核心逻辑
web/      约 1700 行（不含 vendor 依赖）  ← 前端
tools/    约 2600 行 Python   ← 自检与调试脚本
```

`web/vendor/` 里那 18 个文件是第三方库（d3、markmap、marked），不用读。

**建议的阅读顺序**（下一章会详细讲）：

```
run.py  →  src/app.py  →  src/webapi/routes_tasks.py  →  src/pipeline.py
                                                     ↓
                        src/platforms/base.py  →  src/platforms/bilibili.py
                                                     ↓
                        src/llm/notes.py  →  src/core/utils.py
```

不要一开始就看 `bilibili.py`（584 行，全是 B 站接口的细节和踩坑），会劝退。
